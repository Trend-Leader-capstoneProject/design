# 아이디 중복 확인

## 1. 기능 개요

| 항목 | 내용 |
| --- | --- |
| 기능명 | 아이디 중복 확인 |
| API 그룹 | Auth API |
| 관련 화면 | 회원가입 화면 |
| 기능 목적 | 사용자가 입력한 로그인 ID가 이미 존재하는지 확인해 회원가입 UX를 개선한다. |
| 연결 API | `GET /api/auth/check-login-id` |
| 인증 여부 | 불필요 |
| Frontend Client | `publicApiClient` |
| 관련 DB | `users` |

---

## 2. 기능상세명세

| 번호 | 기능 구분 | 기능 명세 |
| ---: | --- | --- |
| 1 | 호출 | Signup 화면에서 `login_id` 입력 후 중복 확인 버튼을 누르면 API 호출 |
| 2 | 입력 검증 | `login_id` 형식이 올바르지 않으면 요청을 막거나 Backend 422를 표시 |
| 3 | 조회 | Backend가 `users.login_id` 기준으로 사용자 존재 여부 조회 |
| 4 | 사용 가능 | 존재하지 않으면 `200`, `is_available=true`, `reason=null` |
| 5 | 사용 불가 | 이미 존재하면 `200`, `is_available=false`, `reason=DUPLICATED_LOGIN_ID` |
| 6 | 상태 초기화 | 사용자가 `login_id`를 수정하면 기존 중복 확인 결과 즉시 무효화 |
| 7 | 최종 중복 방어 | Signup API에서도 중복 재조회 및 DB UNIQUE Constraint를 사용 |
| 8 | 장애 | Network/5xx이면 사용 가능으로 임의 확정하지 않고 미확정 상태 유지 |

---

## 3. Frontend 처리 메모

주요 상태 예시:

```text
loginId
isLoginIdChecked
isLoginIdAvailable
loginIdMessage
isCheckingLoginId
```

### 사용 가능

```text
200
is_available = true
→ 사용 가능 안내
→ 중복확인 완료 상태
```

### 사용 불가

```text
200
is_available = false
reason = DUPLICATED_LOGIN_ID
→ 다른 ID 입력 안내
```

### ID 변경

```text
사용자가 loginId 수정
→ 기존 중복확인 결과 폐기
→ 재확인 필요
```

### Network/5xx

```text
중복확인 미확정
→ 회원가입 가능으로 간주하지 않음
→ 재시도 안내
```

---

## 4. Backend 처리 메모

```text
GET /auth/check-login-id
→ Query Validation
→ users.login_id 조회
→ exists 여부 계산
→ CheckLoginIdData
→ 200
```

중복 ID는 오류 예외가 아니라 정상 조회 결과로 반환한다.

---

## 5. login_id 정책

```text
최소 4자
최대 50자
첫 글자 영문 소문자
허용 문자: a-z, 0-9, _
```

잘못된 요청은 `400`이 아니라 FastAPI/Pydantic Request Validation 정책에 따라 `422`로 처리한다.

---

## 6. 계정 상태와 ID 재사용

현재 MVP에서는 `users` 행이 존재하면 상태와 관계없이 로그인 ID를 재사용할 수 없다.

```text
ACTIVE
→ 사용 불가

SUSPENDED
→ 사용 불가

WITHDRAWN
→ 사용 불가
```

탈퇴 ID 재사용 정책은 회원 탈퇴 기능의 후속 설계에서 별도로 결정한다.

현재 중복확인 기능에서 임의로 WITHDRAWN ID를 재사용 가능 처리하지 않는다.

---

## 7. DB 처리 메모

```text
users.login_id
UNIQUE
```

중복 확인 API는 조회만 수행한다.

다만 실제 Signup에서는:

```text
사전 조회
+
DB UNIQUE Constraint
```

를 모두 사용한다.

---

## 8. Race Condition

다음 상황은 정상적으로 발생할 수 있다.

```text
A → trend_user01 available
B → trend_user01 available

A → signup 성공
B → signup 시도
```

B의 최종 결과:

```text
DB UNIQUE 충돌
→ 409
→ DUPLICATED_LOGIN_ID
```

따라서 `is_available=true`는 "현재 조회 시점에 사용 가능"이라는 의미이며,
향후 Signup 성공을 예약하는 Lock이 아니다.

---

## 9. 예외 처리 상세

| 상태 | 의미 | 처리 |
| ---: | --- | --- |
| 200 | 사용 가능 | `is_available=true` |
| 200 | 이미 존재 | `is_available=false` |
| 422 | 입력 누락/형식 오류 | 필드 오류 표시 |
| 500 | DB/서버 오류 | 재시도 안내 |
| Network | 연결 실패 | 미확정 상태 유지 |
