## 1. 수정 대상 페이지

아래 문서를 각 Notion 페이지의 기존 내용과 교체하는 것을 권장한다.

1. API 명세서 → 회원가입 정보 전송
2. API 명세서 → 아이디 중복 확인
3. 기능상세명세서 → 회원가입 등록
4. 기능상세명세서 → 아이디 중복 확인
5. Error Code
6. API 상세 기능명 템플릿

## 2. 이번 수정의 핵심 결정

### 회원가입 성공

기존:

```text
회원가입 성공
→ 프론트에서 next_step 확인
→ 관심사 선택 화면으로 직접 이동
```

수정:

```text
POST /api/auth/signup
→ 201 Created
→ Access Token + Session 응답
→ AuthProvider.establishSession()
→ Access Token SecureStore 저장
→ AUTHENTICATED
→ RootNavigator가 next_step을 평가
→ INTEREST_SELECTION
```

회원가입 화면은 관심사 화면으로 직접 `navigate`, `replace`, `reset`하지 않는다.

---

### 회원가입 성공 응답

```text
access_token
token_type
user
├─ user_id
├─ login_id
├─ name
└─ status
has_selected_interests
next_step
```

`email`은 인증 Session Response에 포함하지 않는다.

---

### Request Validation

FastAPI/Pydantic Request Validation 실패는 `422`로 통일한다.

```text
422
- 필수값 누락
- login_id 형식 오류
- password 길이 오류
- password_confirm 불일치
- name 형식 오류
- email 형식 오류
```

`400`은 Pydantic Request Validation의 기본 상태 코드로 사용하지 않는다.

---

### 중복 충돌

```text
409 Conflict

data.field
data.reason
```

사용 가능한 `reason`:

```text
DUPLICATED_LOGIN_ID
DUPLICATED_EMAIL
```

Frontend는 한국어 `message` 문자열을 파싱하여 필드를 판별하지 않는다.

---

### 아이디 중복 확인

중복 여부 자체는 조회 결과이므로 중복 ID도 `200 OK`다.

```text
사용 가능
→ 200
→ is_available = true
→ reason = null

이미 존재
→ 200
→ is_available = false
→ reason = DUPLICATED_LOGIN_ID
```

형식 오류는 `422`다.

---

### Race / UNIQUE

```text
1. /check-login-id
   → UX용 사전 확인

2. signup Service 사전 조회
   → 빠른 중복 오류 반환

3. DB UNIQUE Constraint
   → 동시 요청에 대한 최종 무결성 보장
```

알려진 UNIQUE 위반만 `409`로 변환한다.

```text
uq_users_login_id
→ DUPLICATED_LOGIN_ID

uq_users_email
→ DUPLICATED_EMAIL
```

원인이 확인되지 않은 `IntegrityError`는 임의로 `409`로 변환하지 않는다.

## 3. 이메일 길이 정책 메모

현재 DB 컬럼은:

```text
users.email
VARCHAR(255)
```

현재 Backend 요청 타입은:

```text
EmailStr | None
```

이며 `EmailStr`이 사용하는 `email-validator` 계열은 전체 이메일 주소에 자체 길이 제한을 적용한다.

따라서 별도의 `max_length=255`를 추가하더라도 실질적인 허용 범위를 넓히거나 크게 바꾸는 효과는 없다.

### 권고

현재 문서에는 다음처럼 표현한다.

```text
누락/NULL/공백은 None으로 정규화한다.
값이 있으면 EmailStr 기반 이메일 형식 검증을 수행한다.
DB 저장 컬럼은 VARCHAR(255)이다.
```

프로젝트에서 API Schema에 DB 저장 상한을 명시적으로 드러내고 싶다면 `max_length=255`를 추가하는 것도 가능하지만,
현재 이메일 검증 라이브러리의 더 엄격한 제한과 중복되는 방어라는 점을 인지한다.

즉, 이것은 치명적인 누락이라기보다 **계약 가시성/방어적 Validation을 얼마나 명시적으로 둘 것인지의 선택**에 가깝다.
