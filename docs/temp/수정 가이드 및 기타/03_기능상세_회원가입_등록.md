# 회원가입 등록

## 1. 기능 개요

| 항목 | 내용 |
| --- | --- |
| 기능명 | 회원가입 등록 |
| API 그룹 | Auth API |
| 관련 화면 | 회원가입 화면 |
| 기능 목적 | 일반 계정 정보를 기반으로 신규 사용자를 생성하고, 가입 직후 자동 로그인 Session을 확립하여 관심사 선택 단계로 진입할 수 있도록 한다. |
| 연결 API | `POST /api/auth/signup` |
| 인증 여부 | 불필요 |
| Frontend Client | `publicApiClient` |
| 관련 DB | `users` |

---

## 2. 기능상세명세

| 번호 | 기능 구분 | 기능 명세 |
| ---: | --- | --- |
| 1 | 화면 이동 | 사용자가 Login 화면에서 Signup 화면으로 이동한다. 이 이동만 AuthNavigator 내부의 일반 Navigation으로 처리한다. |
| 2 | 화면 입력 | 사용자는 `login_id`, `password`, `password_confirm`, `name`, 선택 `email`을 입력한다. |
| 3 | 사전 검증 | Frontend는 필수 입력과 기본 입력 형식을 확인하고, 로그인 ID 중복 확인 상태를 관리한다. |
| 4 | API 요청 | 회원가입 버튼 클릭 시 `publicApiClient`로 Signup API를 호출한다. |
| 5 | Backend 검증 | FastAPI는 Request Validation, ID/Email 중복 조회, 비밀번호 Hash, User 저장을 수행한다. |
| 6 | Transaction | User 저장의 Commit/Rollback은 AuthService가 소유한다. |
| 7 | 중복 최종 방어 | 사전 조회와 별개로 DB UNIQUE Constraint가 동시 가입 요청의 최종 무결성을 보장한다. |
| 8 | 자동 로그인 | 저장 성공 후 Access Token과 Session 정보를 생성해 201로 반환한다. |
| 9 | Session 확립 | Frontend는 Signup Response를 AuthProvider에 전달하여 Access Token을 SecureStore에 저장하고 인증 Session을 등록한다. |
| 10 | 화면 결정 | SignupScreen이 Interest 화면으로 직접 이동하지 않는다. RootNavigator가 `AUTHENTICATED + next_step`을 평가하여 Interest Selection 화면 Tree를 표시한다. |
| 11 | 예외 처리 | 422, 409, Network, 5xx를 구분한다. 실패 시 사용자의 입력값을 불필요하게 초기화하지 않는다. |

---

## 3. 전체 처리 흐름

```text
Login
→ Signup
→ 입력
→ 로그인 ID 중복 확인
→ Signup 버튼
→ POST /api/auth/signup
→ Request Validation
→ ID/Email 사전 중복 조회
→ Password Hash
→ User 저장
→ Commit
→ Session 계산
→ Access Token 발급
→ 201
→ AuthProvider.establishSession()
→ SecureStore 저장
→ AUTHENTICATED
→ RootNavigator
→ INTEREST_SELECTION
```

## 4. Frontend 처리 메모

| 구분 | 내용 |
| --- | --- |
| 화면 | SignupScreen |
| API Client | `publicApiClient` |
| 입력 상태 | `loginId`, `password`, `passwordConfirm`, `name`, `email` |
| 중복확인 상태 | 확인 여부, 사용 가능 여부, 메시지 |
| 요청 중 상태 | 버튼 중복 클릭 방지 |
| 성공 | AuthProvider에 Token + Session 전달 |
| Token | SecureStore 저장 |
| 화면 전환 | RootNavigator의 선언적 Auth State 분기 |
| 422 | Backend `data.errors[]`를 필드 오류로 연결 |
| 409 | `data.field`, `data.reason`으로 충돌 필드 연결 |
| Network/5xx | 입력 유지 및 재시도 |
| Password | 성공 후 메모리 상태 정리 |

### 금지하는 구조

```text
SignupScreen
→ navigation.replace("InterestSelection")
```

```text
SignupScreen
→ next_step 직접 해석
→ 임의 Navigation
```

### 사용하는 구조

```text
SignupScreen
→ establishSession()
→ AuthState 변경
→ RootNavigator 재평가
```

## 5. Backend 처리 메모

| 구분 | 내용 |
| --- | --- |
| Router | HTTP 요청/응답 계약 |
| Schema | 회원가입 입력 Validation |
| AuthService | 회원가입 Use Case + Transaction + Session 생성 |
| UserRepository | 사용자 조회/저장 |
| Security | `hash_password()`, Access Token 생성 |
| InterestRepository | 가입 직후 Session의 관심사 여부 계산 |
| DB | `users` 저장 및 UNIQUE 최종 방어 |

### 신규 사용자

```text
login_id = request.login_id
password_hash = hash(password)
name = normalized name
email = normalized email 또는 NULL
status = ACTIVE
```

회원가입 단계에서 생성하지 않음:

```text
user_profiles
user_interest_categories
oauth_accounts
```

## 6. 입력 정책

### login_id

```text
4~50자
영문 소문자로 시작
영문 소문자 / 숫자 / _
```

### password

```text
15~128자
trim 금지
원문 저장 금지
```

### password_confirm

```text
password와 정확히 일치
DB 저장 금지
```

### name

```text
trim
1~50자
Unicode 허용
```

### email

```text
선택값
누락 / null / 빈 문자열 / 공백
→ None

값 존재
→ normalize
→ EmailStr 형식 검증
→ DB 저장
```

DB:

```text
VARCHAR(255)
```

## 7. 예외 처리 상세

### 422 Request Validation

다음 입력은 422 대상이다.

```text
필수 입력 누락
login_id 형식 오류
password 길이 오류
password_confirm 불일치
name 형식 오류
email 형식 오류
```

### 409 Conflict

```text
login_id 중복
→ field = login_id
→ reason = DUPLICATED_LOGIN_ID

email 중복
→ field = email
→ reason = DUPLICATED_EMAIL
```

### 500

알 수 없는 DB/서버 오류는 409로 위장하지 않는다.

### Network Error

Frontend는 회원가입이 실패했다고 단정하여 입력을 지우지 않고 재시도할 수 있도록 한다.

## 8. Race / Transaction

사전 중복 확인은 UX 기능이다.

```text
/check-login-id
→ available
```

이어도 다른 사용자가 먼저 가입할 수 있다.

따라서:

```text
사전 조회
+
signup Service 재조회
+
DB UNIQUE
```

를 함께 사용한다.

Known UNIQUE:

```text
uq_users_login_id
uq_users_email
```

Known UNIQUE 위반:

```text
rollback
→ 409 Conflict
```

Unknown IntegrityError:

```text
rollback
→ re-raise
→ 공통 500
```

## 9. 자동 로그인 및 Navigation

가입 성공 Response:

```text
access_token
token_type
user
has_selected_interests
next_step
```

초기 사용자는 관심사가 없으므로:

```text
has_selected_interests = false
next_step = INTEREST_SELECTION
```

Frontend:

```text
201
→ establishSession()
→ Token 저장
→ AUTHENTICATED
→ RootNavigator
→ INTEREST_SELECTION
```

---

## 10. SecureStore 저장 실패

다음 상황을 별도로 처리한다.

```text
Signup API 201
→ User DB 저장 완료
→ Access Token 수신
→ SecureStore 저장 실패
```

이미 회원가입은 끝난 상태이므로 Signup API를 재호출하지 않는다.

```text
Session 확립 실패
→ UNAUTHENTICATED 복구
→ Login에서 재로그인 안내
```
